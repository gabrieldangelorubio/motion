## 0. Cómo leer esto (y qué NO es)

- **Es un contrato, no una guía de estilo.** Cada regla tiene un porqué escrito, porque la regla
  sin el porqué se rompe apenas aparece un caso que no la contempla. Si el porqué no aplica a tu
  caso, decínoslo en la entrega — no la esquives en silencio.
- **Las reglas marcadas 🔴 son duras**: sin ellas el código no entra. Las demás son el sistema; se
  respetan salvo motivo escrito.
- **No hace falta que construyas lo que ya existe.** Login, sesión, permisos, sidebar, tema
  claro/oscuro, idioma, notificaciones, el catálogo de media, el asistente: todo eso ya está. Tu
  módulo **se enchufa**. La §2.9 dice exactamente qué no tenés que hacer.
- **Cuando dudes entre inventar y reusar: reusá.** Un control hecho a mano no tiene el hover, el
  foco, la animación ni el modo oscuro del sistema, y envejece distinto. Si ninguna pieza cubre tu
  caso, **sumale una variante** a la más parecida y anotalo — no la forkees.
- **Los anexos son la verdad literal** (valores, nombres, firmas); las secciones son las reglas.
  Si un anexo y una sección dicen distinto, el anexo salió del código hoy y gana.

## 1. El contexto en una página

**diosa** es la plataforma interna de AdiosAdios (productora audiovisual). Es **modular**: cada
módulo es una herramienta dentro del pipeline de una producción — `cotizar → carpetas →
playground → entregar`. El **proyecto** es la entidad eje: todo cuelga de un proyecto (cronograma,
presupuesto, equipo, media, feedback, generaciones de IA). Un módulo nuevo entra como una
herramienta más **dentro** de un proyecto, con su scoping y sus permisos ya resueltos por el
sistema.

## 2. CÓMO TIENE QUE ENTRAR EL CÓDIGO

Esta es la sección que decide si el trabajo se integra en un día. Léela dos veces.

### 2.1 Tu repo aparte: el mismo esqueleto

Armá tu proyecto con `create-next-app` en **la misma versión** (§1), TypeScript estricto, Tailwind
v4, alias `@/` → `src/`. Reproducí **la misma estructura de carpetas** que va a tener en diosa,
así la entrega es un `cp -R` y no una mudanza:

```
src/
  app/(app)/(modulos)/<ruta>/        ← las pages del módulo (Server Components)
    page.tsx
    acciones.ts                      ← server actions ("use server"), funciones con sufijo …Action
  app/api/<modulo>/…/route.ts        ← route handlers, sólo si hacen falta (subidas, streams, tiempos largos)
  components/<modulo>/               ← la UI del módulo (client components, PascalCase)
  lib/<modulo>/                      ← la LÓGICA PURA (sin React, sin DOM, sin DB): modelo, cálculo, serialización
    *-puro.ts                        ←   lo que se testea solo
    consultas.ts                     ←   lo que SÍ toca la base (server)
tests/<modulo>/                      ← node:test, un archivo por pieza pura (+ fixtures/)
docs/modulos/<modulo>/README.md      ← el diseño del módulo, arranca con «## Norte (goles)» (§2.10)
docs/modulos/<modulo>/backlog.md     ← lo que quedó afuera, priorizado
```

Todo lo demás de tu repo aparte (layout, login falso, sidebar de juguete, tu `globals.css` copiado
del anexo A) es andamiaje tuyo y **no viaja**. Marcalo claramente (`_andamiaje/` o un README)
para que no lo copiemos por error.

### 2.2 🔴 Las tres capas, y la regla que las separa

diosa separa **tres** cosas, y el guardián `check:cliente` lo verifica en cada build:

1. **Lógica pura** (`src/lib/<modulo>/*.ts`): TypeScript sin React, sin `window`, sin base de
   datos. Es lo que se **testea solo** y lo que sobrevive a cualquier rediseño de la UI. Para un
   motor de animación, **esto es el 70 % del valor** (§10).
2. **Capa de datos** (`src/lib/<modulo>/consultas.ts`, server actions, route handlers): lo que
   lee/escribe la base y valida permisos. **Siempre en el servidor.**
3. **UI** (`src/components/<modulo>/*.tsx`): componentes `"use client"` que reciben datos por props
   y llaman server actions para escribir.

**La regla dura:** un componente `"use client"` **no importa VALORES de la capa de datos**, aunque
el valor sea puro — importa lo que el archivo de origen *arrastra*. Nuestro guardián sigue el
grafo de imports de valor desde cada `"use client"`; si llega al cliente de la base, corta el
build. Sin él, la base entra al bundle del browser y la página revienta en runtime con el build
en verde. `import type` es inocuo. Un server action es una
frontera: un componente cliente **puede** importar un action que toca la base — para eso existe.
Si un helper que necesitás en el cliente vive junto a los datos, **extraelo a un archivo puro**.

### 2.3 🔴 Permisos y validaciones: siempre en el servidor

- Todo lo que muta valida **en el servidor**, contra la base, **nunca confiando en el cliente**. La
  UI puede esconder un botón; el server action re-chequea igual.
- **El id que llega del cliente no se confía**: el server deriva a qué proyecto pertenece la cosa y
  verifica que el actor pueda verla/editarla. Un action que recibe `proyectoId` del cliente y lo
  usa sin gatearlo es un IDOR: el chequeo vive en la capa de datos, no en el caller.
- **Fail-closed**: si no se puede verificar, se niega. **Un parámetro de permiso nunca es
  opcional**: un candado que sólo corre «si le pasan el dato» aprueba en silencio a los callers
  que no se lo pasan.
- Vos no vas a poder implementar los permisos reales (no tenés el modelo de usuarios). Lo que sí:
  dejá **un único punto de entrada** por mutación (`exigirEdicion(actor, composicionId)` o
  similar) que nosotros cableamos al sistema real, y **ninguna escritura fuera de ese camino**.
  El tipo ayuda: que la función que escribe pida un `Actor` (`{ id, rol, email }`), no un
  `actorId` — así un caller que se olvide del gate **no compila**.
- **Ninguna mutación externa** (subir a un storage, llamar una API) **antes de que todo lo que
  puede fallar haya pasado**. Primero validar, después escribir afuera, al final registrar. Si
  la escritura externa falla después de que ya hiciste otra, compensá (borrá lo que subiste).

### 2.4 Persistencia: el patrón que ya funciona en los dos lienzos

Los dos lienzos del repo guardan el documento entero en **una columna `jsonb`** y resuelven las
dos pestañas que editan a la vez con **CAS + merge por elemento**. Copiá el patrón tal cual:

- Una tabla por entidad, **aditiva** (nunca renombrar ni borrar columnas). Columnas que ya son
  convención: `id` (`text`, uuid por default), `ownerId` (FK a `user`, `cascade`), `proyectoId`
  (FK, `set null`, nullable), `nombre`, **`contenido` (jsonb con TODO el documento)**,
  `thumbnailUrl`, `createdAt`, `updatedAt` (`$onUpdate`), `createdBy`/`updatedBy` (`set null`).
- **La revisión vive DENTRO del jsonb** (`contenido.rev`), no en una columna: el `UPDATE` es
  condicional — `WHERE id = :id AND coalesce((contenido->>'rev')::int, 0) = :baseRev` — y escribe
  `rev: baseRev + 1`. Cero filas afectadas = alguien guardó antes.
- **Cada elemento lleva `v` (timestamp)** que se estampa al cambiar. Ante conflicto, el server
  **mergea por elemento** (gana el `v` más alto) y reintenta el `UPDATE` condicional; si vuelve a
  fallar, el autosave se apaga y el cliente ve un aviso «otra pestaña editó».
- **Los borrados son lápidas** (`borrados: [{ id, v }]` aparte), no elementos que desaparecen del
  array: sin eso el merge los resucita.
- **El snapshot viaja al server como STRING**, no como objeto anidado: el transporte de los
  Server Actions de Next corta arrays anidados grandes en silencio (nos costó 181 guardados
  fallidos en dos semanas).
- **Entregá la migración como SQL aditivo** (`CREATE TABLE …`) más el fragmento de `schema.ts`
  en Drizzle. **No la apliques a ninguna base nuestra**: las migraciones las aplica una sola
  persona, avisando, y sólo aditivas.
- Media (videos, imágenes, fuentes): **no inventes un storage**. El catálogo de media de diosa
  (`playground_media`, en R2, subida directa desde el browser con presign, poster y thumb por
  convención de nombre) ya resuelve todo eso. Tu módulo **lee** de ahí y **escribe** ahí lo que
  renderiza (§10.2).

### 2.5 Lógica pura primero, con sus tests

- Cada decisión que se pueda expresar sin React vive en un archivo puro con su test en
  `tests/<modulo>/`. Runner: `node --import tsx --test tests/<modulo>/*.test.ts`, sin framework.
  Un test:

  ```ts
  import { test } from "node:test";
  import assert from "node:assert/strict";
  import { interpolar } from "@/lib/motion/keyframes-puro";

  test("entre dos keyframes lineales devuelve el punto medio", () => {
    assert.equal(interpolar([{ t: 0, v: 0 }, { t: 10, v: 100 }], 5), 50);
  });
  ```
- 🔴 **Ver el test en rojo antes de creerle.** Un test que nace verde puede estar probando otra
  cosa (o nada). Rompé la función a propósito, mirá que falle **por la razón correcta**, volvé a
  arreglar. Es el ritual de la casa y te lo vamos a preguntar en la entrega: *«¿qué sabotaje
  viste en rojo?»*.
- Un caso que afirma una **ausencia** («no pasa X») necesita un control positivo al lado: sin
  él, «no pasó» también es verde cuando la maquinaria está rota.
- Los tests puros **no necesitan la base ni secretos** (de nuestro lado se descubren solos y
  entran al gate del CI). Los fixtures (una composición de ejemplo) van en
  `tests/<modulo>/fixtures/`.

### 2.6 Idioma: el castellano es la clave

La interfaz habla castellano e inglés. **Todo texto de UI se escribe en castellano y se envuelve en
`t("…")`**; el castellano ES la clave del diccionario, así que un texto sin traducir se lee en
castellano, nunca roto. En castellano `t(x) === x` (no hay diccionario `es`). En tu repo aparte
alcanza con un stub que cumpla la interfaz real (anexo F):

```ts
// src/lib/i18n/stub.ts — andamiaje para el repo aparte; nosotros lo cambiamos por el real
const rellenar = (s: string, vars?: Record<string, string | number>) =>
  vars ? s.replace(/\{(\w+)\}/g, (_, k) => String(vars[k] ?? "")) : s;
export const t = Object.assign((clave: string, vars?: Record<string, string | number>) => rellenar(clave, vars), {
  idioma: "es" as const,
  plural: (n: number, sing: string, plur: string, vars?: Record<string, string | number>) => rellenar(n === 1 ? sing : plur, { n, ...vars }),
  ctx: (_ctx: string, clave: string, vars?: Record<string, string | number>) => rellenar(clave, vars),
  rico: (clave: string, huecos: Record<string, React.ReactNode>) => clave.split(/(\{\w+\})/).map((p) => huecos[p.slice(1, -1)] ?? p),
});
```

Reglas: `t("Guardar")` · `t("{n} capas", { n })` · `t.plural(n, "capa", "capas")` (singular y
plural son DOS claves) · `t.rico("Guardado en {donde}", { donde: <b>…</b> })` para texto con
formato adentro (nunca aplanes un JSX a string para traducirlo). **Nunca `t(variable)` ni
`` t(`…${x}`) ``**: el guardián extrae los literales, y una variable o un template lo dejan
ciego. Un `Record` de constantes de UI guarda castellano y se envuelve **al pintar**. Nunca texto
de UI en inglés (salvo nombres de marca: Playground, ByeFrame, AdiosJam, Diosa). En el cliente el
traductor real se obtiene con un hook (`useT()`); en un Server Component, con `await traducir()`.

**Números y fechas no se traducen a mano.** Hay un único helper de fechas
(`fechaLocalizada(d, idioma, opts)` con `opts` de `Intl.DateTimeFormat`) y un guardián que corta
si aparece una tabla de meses propia o un `toLocaleDateString("es-AR", …)` con locale a mano. Un
formato de puros dígitos (`24/08`, `14:30`, `00:00:12:05`) no lo necesita. Los timecodes de un
editor de motion son dígitos: no pasan por el idioma.

### 2.7 Dependencias: lo que hay, y cómo se agrega una

Lo que ya existe y tu módulo puede reusar está en el **anexo E**. Antes de agregar una, tres
preguntas: *¿ya hay algo en el repo que lo hace?* (mirá el anexo: hay `mp4-muxer`, `mp4box`,
`sharp`) · *¿pesa en el bundle de TODAS las páginas o sólo en la tuya?* (un módulo nuevo no puede
engordar el shell compartido — §9) · *¿se mantiene?*. Toda dep nueva va en `ENTREGA.md` con su
motivo y su peso, y **de nuestro lado se revisa antes del primer `npm install`** (edad,
mantenedores, `scripts` del paquete). **No entran**: librerías de UI, de íconos, de animación de UI,
de estado global, de canvas, ni `moment`/`dayjs`. Para motion graphics **sí** puede haber deps
legítimas (§10.4).

### 2.8 Convenciones de código (verificadas contra el repo)

- **Identificadores en castellano**, como el resto del repo: `crearComposicion`, `puedeEditar`,
  `capaSeleccionada`, `registrarCuenta`, `asegurarAccionAdmin`. Sin spanglish (`getCapa` no). El

- **Nombres de archivo:** **kebab-case** en `lib/` (`keyframes-puro.ts`, `formato-numero.ts`),
  **PascalCase** en componentes (`Lienzo.tsx`). Sufijos con significado: `*-puro.ts` (sin
  efectos), `acciones.ts` (server actions, con `"use server"` en la primera línea y funciones
  `…Action`), `consultas.ts` (toca la base), `route.ts` (handler).
- **Docblock de cabecera en cada archivo que decide algo**: qué es, **por qué** existe así, y el
  gotcha que resuelve. En diosa los comentarios explican decisiones, no describen el código.
  Modelo real:

  ```ts

     Lógica de cuentas, roles y aprobación (servidor)

     Acá vive lo que tocan tanto las server actions como Auth.js y las pruebas:
     alta de cuenta, verificación de credenciales, detección de admins y las
     operaciones de moderación. Sin dependencias de Next/Auth.js para poder
     probarse de forma aislada (solo necesita la DB).
  ----------------------------------------------------------------------------- */
  ```
- **Errores:** la capa de datos y las server actions devuelven un objeto discriminado por `ok`
  — `{ ok: true, … } | { ok: false, error: string }` — con el mensaje **en castellano y para un
  humano**; `throw` se reserva para lo verdaderamente excepcional. Los route handlers envuelven
  todo en `try/catch` y devuelven `Response.json({ error }, { status })` con el status correcto
  (400 input · 401/403 permisos · 500 catch-all), nunca un stack.
- `"use client"` / `"use server"` en la **primera línea**, sin nada antes. Imports siempre con
  `@/…`, nunca `../../..`.
- **`type` sobre `interface`** para datos (2.165 contra 28 en `src/lib`); `export default` sólo
  en pages/layouts; sin `any` (`unknown` y estrechar).
- **Todo `switch` que mapea DATO → UI lleva un `default` que DEGRADA**, nunca uno que rompe: otra
  sesión puede meter un valor que tu build no conoce, y no puede tumbar la sección entera.
- Un `<input type="number">` no muestra flechas nativas; se edita tipeando.

### 2.10 El paquete de ENTREGA

Entregás un **repo git aparte con acceso de lectura para nosotros** — no un ZIP: sin historia ni

2. **`ENTREGA.md`** en la raíz — es lo primero que leemos:

   - **qué probaste a ojo** (en qué browser, en claro y oscuro, en teléfono) y qué no;
   - **números medidos**: fps del preview con N capas, peso del bundle de tu page.
3. **`docs/modulos/<modulo>/README.md`** que **arranca con «## Norte (goles)»**: para qué existe

### 2.11 Lo que va a correr de nuestro lado

## 3. EL SISTEMA VISUAL

Todo lo de esta sección vive en `src/app/globals.css` (tokens y clases) y se valida en la
**librería viva** `/diseno` — una página que renderiza las piezas REALES en ambos modos. Los
valores literales están en el **anexo A**; acá van las reglas.

### 3.1 🔴 Paleta estricta

**Negro, blanco (en opacidades) y azul `#0005FF`** como único acento de interacción. Más el
semáforo de estado, **sólo para badges y avisos**. Cero colores nuevos: si tu módulo necesita un
color que no está acá (el rojo de un keyframe seleccionado, el color de una pista de audio), **se
consulta y se documenta** — no se mete «porque queda lindo».

| Token | Es | Regla |
|---|---|---|
| `--background` · `--foreground` · `--muted` | fondo · texto · texto secundario | el fondo no es negro puro: las sombras necesitan dónde leerse |
| `--ink` | «tinta» para overlays: blanco en oscuro, oscuro en claro | para velos y hovers (`bg-ink/[0.06]`), no para texto |
| `--acento` | `#0005FF`, idéntico en ambos modos | **único** acento de interacción |
| `--acento-grafico` | el azul aclarado para LÍNEAS de gráfico y texto en oscuro | la única forma legal de azul como texto en oscuro (6,8:1) |
| `--ok` | **es azul** (redirige a `--acento`) | la paleta NO tiene verde |
| `--atencion` | gris | pendiente / en espera |
| `--peligro` | rojo | error · destructivo · rechazado. **Nunca el azul para alertar** |
| `--exito` | verde | **única excepción verde**, sólo el semáforo de capacidad del cronograma. No la uses |
| `--topo` | gris de placa sólida con texto blanco | el negro de la casa como SUPERFICIE |

**La regla del azul (dura):** `#0005FF` tiene luminancia bajísima — como **texto sobre fondo
oscuro es ilegible** (~1.8:1). Se usa como **superficie o señal**: fondos sólidos con texto blanco
(`bg-acento text-white`), barras de 2px, dots, flechas, íconos, guías de snapping. El texto
interactivo va en foreground pleno; texto azul sólo sobre placa clara o con `--acento-grafico`.
Ejemplos canónicos: ítem activo de una lista = texto foreground + barra/ícono azules; link «N →»
= texto foreground + flecha azul; badge de estado = píldora sólida.

**Para un editor de motion graphics** esto significa: la selección se marca con un borde azul
de 1–2px, el playhead es una línea azul, los keyframes seleccionados son azul sólido con
símbolo blanco; «verde = ok» no existe; y los colores que el USUARIO le pone a sus capas son
contenido, no UI — viven en el lienzo, no en el chrome.

### 3.2 Vidrio (glass): una jerarquía, cuatro clases

La separación de superficies la hacen las **sombras y el blur**, no los bordes. Hay UN vidrio por
nivel, y el nivel lo decide **cuánto texto lleva** (más texto = más opaco):

| Clase | Nivel | Blur | Para qué |
|---|---|---|---|
| `.glass` | paneles (~5 % de fondo) | `blur(24px) saturate(180%)` | superficies estructurales sobre el fondo de la página |
| `.glass-deep` | ventanas (~11 %) | `blur(28px)` | modales, drawers |
| `.glass-menu` | menús / popovers / toasts (~90 %) | `blur(30px)` | toda capa flotante: mismo vidrio + `rounded-card` + sombra `--menu-shadow` + `.capa-fade` |
| `.glass-tooltip` | tooltips (~97 %) | sin blur | lo más alto del stack, lo más legible |
| `.menu-solido` | la variante OPACA de `.glass-menu` | ninguno | capas que viven **sobre otra superficie glass** |
| `.panel-solido` / `.panel-solido-deep` | `.glass` / `.glass-deep` sin blur | ninguno | grillas con muchas tarjetas (apilar blur repinta por frame) |
| `.telon-vidrio` / `.telon-solido` | el velo de un modal | con / sin blur | `superficie="solida"` cuando blurear la página entera es costo puro |
| `.glass-interactive` / `.panel-solido-int` | hover de tarjeta clickeable | — | resalte de fondo/borde/sombra, **sin `translateY`** |
| `.capa-alerta` | alerta de error | compone con `.glass-menu` | borde + aura en `--peligro`, nunca azul |
| `.acento-bisel` · `.acento-bisel-sutil` · `.peligro-bisel` | relieve de 1px | — | piezas azules grandes · chips chicos · botones destructivos |

Reglas que no se negocian, con su porqué:

- **Glass sobre glass = OPACO.** Una capa flotante sobre otra superficie con `backdrop-filter`
  (un menú dentro de un modal) **no lleva su propio blur**: apilar blur se pone lento al animar.
  Usá `.menu-solido` (`<Popover superficie="solida">`).
- **Un `backdrop-filter` sobre un lienzo que panea se recomputa POR FRAME.** Dentro de la capa
  de mundo de un canvas, el repo **anula** cualquier utility de blur
  (`.board-mundo [class*="backdrop-blur"] { backdrop-filter: none }`): medido, pasar de 957
  capas compositadas a 55 llevó el pan de 46 ms/32 % de jank a 9 ms/1 %. Para motion graphics
  es central: **nada con blur encima del lienzo ni de la línea de tiempo**. Los avisos sobre un
  board son sólidos (`<BandaAviso>`).
- **Capas flotantes SIEMPRE por portal a `<body>`**: dentro de un ancestro con `backdrop-filter`
  el blur propio se rompe (backdrop root).
- **Nunca `-webkit-backdrop-filter` a mano**: el minificador genera el prefijo; escribirlo rompe
  el blur en Chrome.
- **Blur en mobile:** el displacement `url(#liquid-*)` no anda en WebKit iOS; cada clase liquid
  lleva una base `blur()` real y el `url()` como mejora bajo `@media (hover: hover) and
  (pointer: fine)`. Nunca sólo el `url()`.
- **Nunca `color-mix()` con `var()` escrito directo en una propiedad**: el compilador de CSS lo
  puede borrar sin avisar. Dentro de una custom property pasa intacto.

### 3.3 Escalas únicas

- **Radios:** `rounded-control` 10px · `rounded-card` 16px · `rounded-panel` 20px. Nada más.
- **Relieve:** `shadow-control` (un control en relieve: luz arriba, apoyo abajo) · `shadow-hueco`
  (hundido: inputs, tracks, contenedor de un segmentado) · `.acento-bisel` (bisel azul con línea
  blanca calada). La separación de paneles la hacen las sombras, no los bordes.
- **Tipografía:** `font-sans` es el stack del sistema (`-apple-system, "SF Pro Text", "Segoe
  UI", Roboto, …`); **no hay webfont cargada** ni `next/font`. `font-mono` (`ui-monospace, "SF
  Mono", Menlo`) para **datos y atajos**. Títulos con `tracking-tight` (−0.02em) y, para un
  hero, `.gradient-text`.
- **Label chiquito en mayúsculas** (el rótulo de todo campo, columna, sección): **una sola
  escala**, `<Etiqueta>` / `CLASE_ETIQUETA` = `text-[11px] font-medium uppercase
  tracking-[0.02em] text-foreground/50`. No copies el string: importá el componente.
- **Todo número que se compara con otro va en `font-mono tabular-nums`** (un timecode, una
  duración, un porcentaje): sin eso los dígitos tienen anchos distintos y las cifras BAILAN entre
  filas. Los KPI van en `<Cifra>`.
- **Input de texto a 16px** (`text-base`): evita el zoom de iOS. Si choca con un control más bajo
  en la misma fila, **subí el otro**.
- **Mismo alto en una fila de controles (regla dura):** buscador + filtro + botones de una toolbar
  comparten alto. `items-stretch` en el contenedor y listo; en los botones-ícono de un gutter,
  `h-7` (28px) para todos.
- **Z-index:** escala 0–9000 y nada de la app pasa de 9000 (banda reservada del sistema, lo vigila
  un guardián). Convención: modal 60 · popover/menú 70 (69 el backdrop) · sheet 80 · visor 80 ·
  píldora fija 90. Tu editor vive en 0–50.

### 3.4 Layout

- `<Contenedor ancho="lectura|panel|completo">` decide el ancho **por función**: `lectura`
  (forms, listas) · `panel` (dashboards) · `completo` (full-bleed: herramientas, galerías,
  **editores** — un lienzo de motion graphics es `completo`). Grillas con `<Grilla>` (líquida,
  `auto-fill + minmax`, sin breakpoints duros).
- **Toda vista va extendida al máximo y no hay botón para achicarla** (`<ContenedorExpandible>`
  sin toggle). Un tablero de columnas **usa todo el ancho** (flex-grow por peso; piso medido por
  contenido; lo vacío se encoge).
- **Márgenes laterales simétricos:** el gap contenido↔sidebar iguala el gap contenido↔borde
  derecho. Es padding del shell (`<main>`), **no de cada página**: tu page no pone padding
  lateral propio.
- **El header de una vista se PEGA (sticky)** con `<BarraSticky superficie="vidrio"
  nivel="vista" sangrado>` y lleva el título en `<TituloPegado>` cuando scrollea (una barra
  pegada sin decir de qué sección es, es un buscador huérfano). Trampas: el contenedor padre **no
  usa `gap`** (la barra aporta dos hijos al flex) y **nunca `position: relative` desde CSS propio**
  sobre ella (le gana a `sticky`).
- **Header de vista:** `<HeaderVista>` — título en **MAYÚSCULAS** (se pasa en Sentence case),
  conteo en mono pegado al título, acciones de la COLECCIÓN (crear), nunca de un ítem.
- **Una tabla con filas heterogéneas usa columnas fijas + cabecera** (`table-fixed` +
  `<colgroup>` + `<thead>` con `<Etiqueta>`); la celda vacía se muestra vacía («—»), nunca se
  colapsa la columna.

### 3.5 Claro y oscuro, siempre los dos

El tema es la clase `light` en `<html>`, puesta por un script de arranque (sin flash); **oscuro es
el default** (`:root`). **Todo cambio visual se valida en ambos modos** — es un requisito de
entrega, no una cortesía. Los tokens ya cambian solos; lo que se rompe son los colores
hardcodeados (§11) y lo que pintás a mano en un `<canvas>` (una regla de tiempo, un waveform):
ahí leé los mismos tokens con `getComputedStyle(document.documentElement).getPropertyValue("--…")`
y volvé a pintar cuando cambie la clase de `<html>` (un `MutationObserver` sobre `class`).

## 4. MOVIMIENTO — la grilla de animación

Un **único lenguaje de movimiento**, no animaciones por componente. Vive en `globals.css` y en
tres piezas. Todo lo que se mueve en diosa usa esto; un módulo de motion graphics **anima
contenido** con su propio motor (§10), pero **su interfaz** se mueve con esta grilla.

### 4.1 Tokens

```css
--ease-suave:  cubic-bezier(0.22, 1, 0.36, 1);   /* la ÚNICA curva: ease-out sin overshoot, nada rebota */
--dur-emerger: 200ms;                             /* entrada de toda capa flotante */
--dur-salir:   150ms;                             /* salida, más rápida que la entrada */
```

- Micro-interacciones (hover, press, toggles): `duration-200 ease-out`. Press: `scale(.97)` en
  90 ms. Alto animado: 260 ms. Nada más largo salvo una escala de módulo (§4.4).
- **`prefers-reduced-motion` → fade corto (120 ms, sólo opacity), siempre.** Nada se salta esta
  regla, tampoco un lienzo: con reduced-motion tu preview sigue reproduciendo (es contenido), pero
  la UI alrededor deja de deslizar y de escalar.

### 4.2 🔴 Reglas

1. **Toda capa flotante anima también al CERRARSE.** Se hace con `usePresencia`, que mantiene el
   nodo montado durante la salida y expone `estado` para ponerlo en `data-estado`; el CSS elige
   entrada o salida por ese atributo. Nunca desmontar de golpe.
2. **Los menús anclados a un botón crecen en ALTO animando sólo `height` — NO `transform`.** Un
   `transform ≠ none` sobre una capa con `backdrop-filter` la vuelve «backdrop root» y le mata el
   blur. Es `<MenuFlotante>`. Corolario: las animaciones de entrada usan `backwards` (al terminar,
   el transform vuelve a `none`) y las de salida `forwards` con desmontaje inmediato.
3. **Tooltips y toasts → `.capa-fade`** (opacity + un slide de `--capa-ty: 4px` + `--capa-escala:
   .98`). **Ventana que ya usa `transform` para posicionarse → `.capa-opaco`** (sólo opacity).
   **La hoja mobile → `.hoja`** (sube desde abajo animando `transform`: puede, porque su
   superficie es sólida y no hay backdrop que romper).
4. **Un desplegable NACE de su botón:** al abrir, el trigger se vuelve el tope (o el piso) del
   menú — misma superficie, mismo borde, el lado que se funde a 90°. Hace FLIP hacia arriba si no
   hay lugar. Expande en el frame **siguiente** al montaje (`requestAnimationFrame`): si naciera
   ya expandido no habría transición que ver.
5. **Nada «salta» hacia arriba al hover** (ni botones): el feedback es **resalte** (hover) o
   **press** (`scale .97` al click). `translateY` en hover está prohibido.
6. **Un panel que al cerrarse tiene que EMPUJAR a un vecino** se colapsa con grid
   `grid-template-rows: 1fr ↔ 0fr` + hijo `min-h-0 overflow-hidden` + fade, **no** con
   `usePresencia` (mantiene el alto y hace saltar el layout). Es `<PanelColapsable>`. ⚠️ Ni un
   píxel de padding en el hijo que colapsa (con `border-box`, `height: 0` no se come el padding);
   el espaciado va en un `<div>` adentro. ⚠️ Un campo de formulario no va dentro del clip: su
   anillo de foco es un `box-shadow` por fuera del borde y `overflow-hidden` lo recorta.
7. **Un toggle de panel no cambia de ícono: anima el suyo** (`<IconoPanelLateral>`; el chevron de
   un colapsable ROTA 180°). Dos íconos que se reemplazan obligan a leer un símbolo nuevo; un
   bloque que se mueve ES la respuesta al click.
8. **Una miniatura que entra crece en `scale`, nunca en `width`** (`width` es layout: empuja a
   las vecinas y era el 85 % del CLS de carga de un lienzo). Lo que aparece en una grilla al
   cambiar filtros: `.grilla-aparece` (280 ms, opacity + 8px + scale .985).

### 4.3 Las piezas (firmas reales)

```ts
usePresencia(abierto: boolean, duracionSalida = 150): { montado: boolean; estado: "abierto" | "saliendo" }
// ⚠️ duracionSalida TIENE que coincidir con --dur-salir; si no, el nodo se va antes o después que la animación.

<AlturaAnimada className?>{children}</AlturaAnimada>
// mide con ResizeObserver y transiciona height (260ms); el padding va DENTRO del hijo medido.

<PanelColapsable titulo resumen? resumenInline? abiertoInicial={true}>{children}</PanelColapsable>
// colapso por grid 1fr↔0fr; el resumen queda visible siempre; resumenInline = título + resumen en un renglón.

<MenuFlotante abierto onClose pos={PosMenu | null} direccion="abajo" | "arriba" anclaRef? superficie="glass" | "solida" tituloHoja?>
// type PosMenu = { x: number; y: number; width: number; lleno: boolean }
// crece en alto desde detrás del botón; por portal; en teléfono devuelve un <Sheet>.
// anclaRef: con ella se cierra sólo si el disparador SE MOVIÓ (>4px), no ante cualquier `scroll` del documento
// (una card que se pliega dispara un re-clamp de scrollY que el browser emite como scroll — medido con Chrome real).
```

### 4.4 Escala de tiempos propia de un módulo

Un módulo **puede** declarar su propia escala **sobre el mismo lenguaje** (misma curva,
`usePresencia`, reduced-motion). Dos precedentes: el Playground (`--pg-dur-emerger: 800ms`,
`--pg-dur-salir: 600ms`, `--pg-step: 80ms` — lo que aparece en el módulo va ~4× más lento y
**escalonado** por `--i`) y el shell del asistente (`.diosa-dock`, `.diosa-barra`: sube y se
expande desde el tile; la salida es una coreografía en tres tiempos). Si tu módulo necesita
tiempos distintos (un inspector que se despliega más lento, un playhead que no se anima nunca),
declaralos como tokens con prefijo (`--mg-*`) y documentá el porqué en el README del módulo. Lo
que NO se hace: un `transition: all 300ms` suelto.

## 5. BOTONES

No hay un componente `<Boton>` único: el sistema es **una clase de comportamiento** (`.boton`)
que da los ESTADOS, más las utilities de color/forma por variante, más dos piezas para los casos
con marco. Las clases, literales del repo:

```css
.boton {                       /* comportamiento común: transición 200ms --ease-suave en transform/bg/border/shadow/color/opacity */
  /* :active → transform: scale(.97), 90ms · :disabled / [aria-disabled="true"] → opacity .55, pointer-events none */
}
.boton-icono { /* igual, pero :active → scale(.9) */ }
/* prefers-reduced-motion: reduce → sin transform en hover/active, sólo cambia el color */
```

| Variante | Clases (copiá tal cual) | Cuándo |
|---|---|---|
| **Primario** (azul sólido) | `boton acento-bisel rounded-control bg-acento px-4 py-2.5 text-sm font-semibold text-white hover:bg-[color-mix(in_oklab,var(--acento)_82%,white)] disabled:opacity-40` | la acción principal de la vista o del modal — UNA por superficie |
| **Secundario** (glass, neutro) | `boton inline-flex h-9 items-center gap-2 rounded-control px-4 text-[13px] shadow-control disabled:opacity-40` | todo lo demás |
| **Peligro** | reposo idéntico al neutro; sólo cambia el hover: `hover:bg-peligro/10 hover:text-peligro` (con marco: `hover:border-peligro/30`) — el botón grande destructivo lleva `peligro-bisel` | borrar, rechazar. **No grita hasta que lo apuntás** |
| **Botón-ícono enmarcado** | `<BotonIcono tam={36} tono="neutro" \| "peligro" activo?>` (`boton-icono grid shrink-0 place-items-center rounded-control border shadow-control`) | cerrar ×, expandir ‹/›, editar, descargar. `activo` = toggle (pone `aria-pressed`) |
| **Chip-botón** | `<BotonChip icono="check" \| "cerrar" etiqueta tono>` | confirmar/rechazar en una fila. `etiqueta` es el aria: nombrá la COSA |
| **Grupo pegado** | `<GrupoBotones botones alto={8 \| 9}>` | una fila de botones que comparten borde |

Estados: **hover** = resalte de color/fondo (`hover:bg-ink/[0.06]`, `hover:bg-acento/85`), nunca
movimiento · **press** = la compresión (`scale .97`), no las dos cosas · **disabled** =
`disabled:opacity-40` · **cargando** = se reemplaza el contenido por `<Spinner tam="sm">` (hereda
`currentColor`: blanco en un botón azul).

Altos que se usan: `h-7` (28, gutter) · `h-8` (32) · `h-9` (36, el default de `BotonIcono`) ·
`coarse:h-11` (44, piso táctil). **Mismo alto en una fila**: `flex items-stretch`.

Reglas transversales:

- **Botón-ícono enmarcado = `<BotonIcono>` siempre** — no copies sus clases (estaban duplicadas
  nueve veces antes de la pieza). Cuando mide menos de 44, él mismo agrega el piso táctil.
- **El rótulo de un botón-ícono lo pone `<ConPista>`** (el tooltip del sistema), nunca un `title`
  nativo ni texto al lado.
- **Piso táctil de 44px** en todo lo que se toca con el dedo (§8.4): se achica lo que se **ve**,
  no lo que se **aprieta** (un ✕ de 20px pintados dentro de un área de 36–44). Hay clases hechas:
  `CLASE_TOQUE` (extiende el toque con un `::after` de 44×44), `_ANCLADO` (para controles
  `absolute/fixed`), `_FILA` (sólo ensancha en vertical, para no robarle el toque al vecino).
- **Acción peligrosa = rojo `--peligro`**, nunca azul: el azul de marca no es color de alerta.

## 6. ÍCONOS

**Un ícono por concepto, del registro, NUNCA un SVG inline.** Sin la regla terminás con nueve
«trash» distintos (pasó de verdad). El registro es `src/components/icons.tsx`:

```tsx
function base(props: IconoProps) {           // TODO ícono comparte esto
  return { width: 20, height: 20, viewBox: "0 0 24 24", fill: "none", stroke: "currentColor",
           strokeWidth: 1.6, strokeLinecap: "round", strokeLinejoin: "round", ...props };
}
const ICONOS = { proyecto: (p) => <svg {...base(p)} aria-hidden>…</svg>, /* … */ } as const;
export type NombreIcono = keyof typeof ICONOS;
export const NOMBRES_ICONOS = Object.keys(ICONOS) as NombreIcono[];   // la librería /diseno los lista sola
export function Icono({ nombre, ...props }: { nombre?: NombreIcono } & IconoProps) { … }
```

Uso: `<Icono nombre="basura" className="text-peligro" />`, `<Icono nombre="play" width={16}
height={16} />`. **Color siempre `currentColor`** (hereda del texto); tamaño default 20px, se pisa
con `width`/`height` o con la clase; `aria-hidden` en el SVG y el `aria-label` en el botón que lo
contiene.

**Cómo se agrega uno:** una entrada más en `ICONOS` con el mismo `base()` (mismo `viewBox`,
`strokeWidth 1.6`, sin fills salvo que el concepto lo pida), y aparece solo en `/diseno`. Si tu
módulo necesita íconos nuevos (keyframe, rombo, capa, máscara, solo/mute, onion skin…),
**entregalos en un archivo aparte `iconos-motion.tsx` con el mismo formato** y nosotros los
fusionamos. Antes de dibujar uno, mirá la lista del **anexo B**: ya hay `play`, `pausa`,
`cuadroAdelante`, `cuadroAtras`, `motion`, `camaraLenta`, `planos`, `mascara`, `pincel`, `tijera`,
`duplicar`, `deshacer`, `repetir`, `ojo`/`ojoTachado`, `candado`, `grip`, `foco`, `paleta`.

Canon que ya está fijado (no inventes un glifo nuevo para estos conceptos): trash = `basura` ·
editar = `lapiz` · reloj = `reloj` · proyecto = `proyecto` · persona = `persona` · cliente/org =
`personas` · sede = `edificio` · fechas = `calendario` · estado = `check` · tipo/rol = `etiqueta` ·
moneda = `dolar` · módulo = `cubo` · origen = `enlace` · prioridad/alerta = `alerta`. ⚠️ Dos
controles vecinos no comparten glifo aunque el canon lo sugiera: a 15px se leen como el mismo
botón repetido.

Fuera del registro hay unos pocos íconos exportados como componentes propios porque tienen
estado o animación (`IconoPanelLateral`, `IconoOjo`…) — anexo B.

## 7. LOS CONTROLES DEL SISTEMA (catálogo de `src/components/ui/`)

**Antes de construir un control, buscá el que ya existe.** Ninguno de estos se rehace a mano; si

## 8. GESTOS E INTERACCIÓN

### 8.1 Teclado y foco

- **Foco al campo primario, automático**, al abrir algo cuyo gesto principal es escribir (un
  editor, un modal, una vista con buscador). En modales el foco es ROBUSTO: `useAutoFoco(activo)`
  reintenta hasta 12 frames (dentro de un portal, `autoFocus` nativo falla). **En touch no se
  auto-enfoca** (salta el teclado): gateado a `esPunteroFino()`.
- **⌘F** recupera el buscador de la vista (lo hace `<Buscador>`, apropiándose del find del
  browser). **Esc** cierra la capa de más arriba (hay pila: las hojas saben cuál es la última).
  **Enter/blur guarda, Esc cancela** en toda edición inline.
- **Los atajos de un editor** siguen la convención que ya tienen los dos lienzos (§8.3) y que el
  usuario trae de Figma/After Effects: `⌘Z`/`⇧⌘Z` · `⌘C`/`⌘V` · `⌘D` · `⌘A` · `Delete`/`Backspace`
  · `Esc` cancela el gesto en curso y deselecciona · `Space` (mantenido) = mano · `⌘0` = escala 1 ·
  `⇧1` = encuadrar todo · una letra por herramienta (`V` seleccionar · `H` mano). **Nunca**
  capturar un atajo mientras el foco está en un input o un `contenteditable` (los dos lienzos
  tienen un `enInput()` que lo chequea primero, salvo `Space`), y **nunca pisar ⌘V/⌘C nativos
  cuando hay texto seleccionado**.

### 8.2 Puntero: fino vs grueso

- **`pointer: fine`** (mouse): hover-peek, tooltips, cursores de resize, hover-scrub de
  miniaturas. **`pointer: coarse`** (dedo): el «hover» es un tap — nada se abre al rozar un borde;
  los targets crecen a 44px (`coarse:` es un variant de Tailwind del repo); lo que sólo se ve al
  hover se ve siempre (`coarse:text-foreground/40` en el lapicito de `TextoEditable`).
- **Hover que ofrece algo, sólo donde hay algo que ofrecer**; una superficie que se abre al hover
  **flota, no empuja** (si empujara, rozar el borde haría saltar la página). El peek no persiste.
- Feedback del click: **press `scale .97`**; del hover: **resalte**. Nada se eleva.
- Un híbrido con mouse (Surface, iPad con trackpad) sigue el camino de escritorio: el gate de
  gestos táctiles es `pointerType !== "mouse"`, no el tamaño de pantalla.

### 8.3 Los lienzos: el vocabulario que ya tienen los usuarios

diosa tiene **dos lienzos infinitos** — el **AdiosJam** (tablero libre tipo Figma/Miró) y el
**board del Playground** (nodos con cables). Un editor de motion graphics es el tercero, y **tiene
que sentirse como los otros dos**: mismos gestos, mismas constantes, mismo guardado. Los dos
comparten la matemática pura de cámara (`lib/canvas/gestos.ts`, `encuadre.ts`, `pinch.ts`) y cada
uno la consume desde su orquestador; ninguno usa librería. Lo que sigue está copiado del código,
con las constantes literales — **usá las mismas**, y aislá tu matemática de cámara en un archivo
puro con estas mismas funciones (`interpretarWheel`, `camaraConZoom`, `pantallaAMundo`,
`camaraQueEncuadra`): al integrar, la reemplazamos por la del repo y no se nota.

| Gesto | Cómo es en los dos lienzos | Constantes |
|---|---|---|
| **Pan (rueda / trackpad)** | `wheel` sin ⌘/ctrl = pan; listener nativo con `{ passive: false }` sobre el viewport; `deltaMode` normalizado (línea = 16px, página = 400px). **Se compone sobre la cámara OBJETIVO, nunca sobre la eased visible** (componer sobre la eased pierde ~⅓ del gesto: bug histórico) | `PAN_MAX = 400` px/evento |
| **Pan (Space + drag / herramienta mano)** | `Space` mantenido (sin repeat) → `manoEfectiva`; `pointerdown` en el viewport, `move`/`up` en `window` (**sin** `setPointerCapture` en escritorio) | — |
| **Zoom** | `wheel` con ⌘/ctrl = zoom **al cursor**: `escala' = clamp(escala·factor)`, `k = escala'/escala`, `x' = px − (px − x)·k`. Rueda discreta: `factor = PASO_RUEDA^(±pasos)`; trackpad/pinch continuo: `factor = exp(−d·K_PINCH)` con `d` acotado. Rueda vs trackpad se distingue por **magnitud**, no por «delta entero» (falla con Magic Mouse) | `PASO_RUEDA = 1.377` · `K_PINCH = 0.009` · `DELTA_MAX = 12` · `UMBRAL_RUEDA = 40px` · `MIN_ESCALA = 0.3` · `MAX_ESCALA = 6` (piso dinámico por encuadre, absoluto `0.04`) |
| **Reset / encuadre** | `⌘0` → escala 1 · `⇧1` → `camaraQueEncuadra(bbox(elementos), rect, { min, max, margen })` | margen 100px escritorio · 16px teléfono |
| **Drag de elementos** | Pointer Events; `pointerdown` en el elemento, `move`/`up` en `window`; el arrastre arranca al cruzar el **umbral** (y recién ahí se registra el checkpoint de undo). `Shift` = eje dominante · `Alt` = duplica y arrastra la copia (alternable en vivo) · `⌘/ctrl` = sin snapping. Selección múltiple se mueve por delta con los orígenes guardados; los `bloqueado` no se mueven | `UMBRAL = 4px` (AdiosJam) / `3px` (Playground) |
| **Selección** | click = reemplaza · shift-click = toggle · **marquee** desde el fondo (`elementosEnRect` compara la caja transformada; las secciones NO entran al marquee) · `⌘A` = todo (contextual: si hay texto seleccionable bajo el foco, selecciona texto) | — |
| **Snapping (sólo AdiosJam)** | `snapArrastre(movido, otros, escala, thresholdPx)`: por cada otro elemento, 3 líneas imán por eje (borde-inicio · centro · borde-fin); **un solo ganador por eje** (la distancia mínima dentro del umbral — evita jitter); devuelve `{ dx, dy, guias }` en coordenadas de MUNDO; las guías se dibujan a **1px constante en pantalla, en azul de marca**. Es el algoritmo canónico (Konva/tldraw/Excalidraw). **Pendiente y declarado:** equal-spacing y snap en resize | `thresholdPx = 8` (÷ escala) |
| **Resize (sólo AdiosJam)** | 8 handles (`nw n ne e se s sw w`) de tamaño constante en pantalla; `Shift` + esquina mantiene aspecto anclado en la opuesta; un elemento con alto por contenido sólo ofrece `e`/`w`; cursores por handle | `MIN = 40px` por lado |
| **Coordenadas** | `pantallaAMundo(sx, sy, rect, cam) = { x: (sx − rect.left − cam.x) / cam.escala, y: … }`; inverso inline `sx = x·escala + cam.x`. Sólo traslación + escala uniforme (no hay rotación en el modelo de los lienzos — en motion graphics SÍ la vas a tener: tu matriz es tuya) | — |
| **Atajos** | `⌘Z`/`⇧⌘Z` · `⌘D` duplica · `⌘C`/`⌘V` (envelope propio + clipboard del SO) · `⌘A` · `Delete`/`Backspace` · `Esc` · `⌘0` · `⇧1` · `V/H/C/X/L/E` herramientas · `N/T/S/R/F` crean en la posición del cursor. Un solo `useEffect` con `keydown`/`keyup` en `window`, `if (enInput()) return` salvo Space, `if (meta) return` para no pisar lo nativo | — |
| **Undo / redo** | stack de **snapshots completos** (`structuredClone` del doc), `pasado`/`futuro` en refs; `registrar()` **antes** de cada mutación relevante (un drag entero es UN paso, no un paso por frame); con una generación IA en vuelo, undo/redo se frenan (pisarían el `v` de lo que está llegando). Historial **por página** | tope **120** entradas |
| **Autosave** | debounce tras el último cambio + flush inmediato en `focusout`/cambio estructural + tope de espera; guard de solapamiento; hash del snapshot contra el último guardado (no guarda lo idéntico); CAS + merge por elemento (§2.4); tras N fallos seguidos se apaga y avisa, distinguiendo fallo de red | debounce `500ms` (AdiosJam) / `1500ms` + `MAX_WAIT 5000ms` (Playground) · `MAX_FALLOS = 5` · reintentos de CAS: 1 / 5 |
| **Touch** | `usePinchZoom`: 1 dedo = pan · 2+ = pellizco (`factorDe(distAntes, distAhora)` acotado por paso); cambiar la cantidad de dedos **re-basa, no emite paso** (si no, la cámara se teletransporta); **acá SÍ `setPointerCapture`** (única vez en el sistema) y por eso el tap guarda el destino en el `pointerdown`; `touch-action: none` en el viewport; **sin inercia** (ya hay ease en el loop). En teléfono el AdiosJam es **sólo lectura** (decisión de producto) | `FACTOR_MAX_PASO = 1.6` · `TAP_MAX_PX = 10` · `TAP_MAX_MS = 500` · `DIST_MINIMA = 1` |
| **Persistencia** | `contenido: jsonb` con `{ paginas: [{ id, nombre, elementos, conectores, borrados }], paginaActiva, rev }`; elemento = `{ id, tipo, x, y, w, h, datos, bloqueado?, v? }` con `datos` discriminado por `tipo`; acceso `nivelDeAccesoTablero(actor, id): "edicion" \| "lectura" \| null` derivado del proyecto | — |

**Cómo hacen 60 fps** (es lo que te vamos a medir, §9): la cámara **no vive en `setState`
durante el gesto** — un loop de `requestAnimationFrame` escribe `style.transform =
"translate(tx,ty) scale(s)"` sobre UN wrapper (`will-change: transform` **sólo ahí**, nunca por
elemento: «con 159 elementos serían 159 capas»), y React se entera al aquietarse (o a ~8 Hz
durante el gesto). Cada elemento se posiciona con `translate3d` y recibe la escala como CSS
var (`--cam-escala`), no como prop — así no rompe su `memo`. Culling geométrico con histéresis
(recalcula si el pan cruzó el 25 % del viewport o el zoom el 15 %). Antes de construir un objeto
nuevo por frame se pregunta un booleano (`hayQueMover`): nada de basura para el GC 60 veces por
segundo. Y a escala chica un `<video>` se pinta como su poster (`UMBRAL_LOD = 0.6`): fue la
palanca que bajó los videos montados de 80 a 20.

### 8.4 Teléfono

El teléfono se **mide, no se opina**: hay tres sondas con Chrome real (`probar:mobile` —
desborde, inputs < 16px, taps < 44 · `sonda:mobile-int` — 14 escenarios con toques reales ·
`sonda:controles` — censo de taps con hit-test). Las reglas que le importan a un módulo nuevo:

- **Dos gates distintos:** «teléfono» (`max-md:` / `useEsMobile()`, ancho < 768) decide la
  **FORMA** (una hoja en vez de un popover, una barra inferior en vez de una lateral); «dedo»
  (`coarse:` / `usePunteroGrueso()`) decide los **TAMAÑOS** (44px). No se confunden: un iPad
  apaisado con dedo no es un teléfono.
- **`<Sheet>`** es la hoja que sube desde abajo (sólida, con agarradera, arrastre para cerrar,
  safe-area y teclado, scroll del body bloqueado, pila de hojas). `Popover`, `MenuFlotante`,
  `Desplegable` y `Modal` (pantalla completa) la heredan solos en teléfono — si usás las piezas
  del sistema, tu módulo ya es mobile.
- **Tokens:** `--safe-t`/`--safe-b` (notch y home indicator; sin `viewportFit: "cover"` valen 0),
  `--barra-inferior` (3.5rem bajo 768px), `--teclado` (lo que tapa el teclado virtual, lo escribe
  `useTecladoVirtual`). Algo anclado al borde inferior suma `--safe-b` + `--barra-inferior`;
  nunca un número fijo.
- **Nada desborda horizontalmente. Nunca.** Lo que no entra en una caja que scrollea deja de
  existir. Texto de input ≥ 16px. Si sólo se llega con hover, en un teléfono no existe. Cuando
  los botones no entran se agrupan (`<MenuDesborde>`), no se apilan. Un gesto de escritorio (⌘,
  click derecho, drag HTML5) no se traduce solo: cada uno necesita su alternativa de un toque.
- Un editor de motion graphics **no tiene que funcionar entero en un teléfono** — pero **no puede
  romperse**: el lienzo se ve, se panea con un dedo y se pellizca con dos, y lo que no entra queda
  en una hoja. El precedente es el AdiosJam: **en teléfono es visor**. Decilo en `ENTREGA.md`.

### 8.5 Arrastrar archivos

El patrón canónico (repetido en ~19 lugares; el modelo es `SoltarDocumento.tsx`): cuatro handlers
`onDragEnter/Over/Leave/Drop` con `e.preventDefault()` obligatorio en `dragover`; se filtra por
`e.dataTransfer.types.includes("Files")` (para distinguirlo de un marquee interno); un **contador
de profundidad** en un ref (`dragDepth`) evita que el overlay parpadee al cruzar hijos; la
validación de tipo/tamaño en el cliente es **cortesía, no el candado** — el server re-valida. Para
soltar media sobre el lienzo de un editor: el drop crea la capa en la posición del cursor
(`pantallaAMundo`) y la subida va por el catálogo de media (§10.2), nunca por un endpoint propio.

## 9. RENDIMIENTO — lo que se mide y los techos

diosa mide su velocidad con instrumentos que corren en el gate de deploy. Un módulo nuevo entra
**sin mover estos números**:

| Qué | Techo | Cómo se mide |
|---|---|---|
| **Peso de cliente del shell** (el JS que paga TODA página) | no crece por un módulo nuevo | `guardia:peso` (dentro del preflight) |
| **Peso de la página del módulo** | dentro del presupuesto por página | ídem |
| **Piso del server** (la sección más rápida = el costo del shell) | 350 ms | `medir:velocidad --presupuesto` |
| **Cualquier sección** | 800 ms | ídem |
| **Pan de un lienzo** (N=120 elementos, headless) | **p95 ≤ 20 ms · jank ≤ 5 %** (la curva sana da ~9 ms · 1 %) | `medir:board --presupuesto` |

Lo que eso significa para tu código:

- **Code-splitting obligatorio de lo pesado.** El motor de render, un encoder, una librería de
  fuentes: `next/dynamic` con `ssr: false` y **sólo en la page del módulo**. Nada de eso puede
  entrar al chunk compartido. (El logo de marca costó 60 KB comprimidos en toda página durante un
  mes por importar un archivo de paths desde un componente compartido.)
- **Un `pointermove` no re-renderiza React.** El pan, el zoom, el drag y el scrub del playhead se
  hacen con refs + `requestAnimationFrame` + `transform` en CSS (o directo sobre el canvas); el
  estado de React se toca **al soltar** (§8.3, «cómo hacen 60 fps»).
- **Nada con `backdrop-filter` sobre lo que se mueve** (§3.2). Ningún displacement `url()` cerca
  de un canvas que reproduce. Un `will-change` por cosa que se mueve sola, no por capa.
- **Las queries de la page en paralelo, no en fila** (`Promise.all`), y una sola ida a la base por
  entidad. Una page que encadena round-trips es lo que hace saltar el techo de 800 ms.
- **Reproducir a 60 fps en preview es un requisito; renderizar es otra cosa** (§10.3).

Para calibrarte, la curva medida de los lienzos actuales (DOM + `transform`, build de
producción): **N=120 → pan p95 9,5 ms · 0 % jank** · **N=240 → 14,9 ms · 0 %** · **N=500 → 35,8
ms · 8 % (con GPU real: 49 ms · 80 % jank, 26 fps)**. O sea que el DOM aguanta ~240 elementos
por página y se rompe llegando a 500; a partir de ahí lo que corresponde es `<canvas>`. Un
editor de motion graphics con capas + keyframes + un preview que reproduce está del lado del
canvas desde el día uno (§10.3). Y lo que **no** movió la aguja cuando se optimizó (para que
no lo repitas): congelar la grilla de fondo · memoizar la capa entera de nodos · culling más
agresivo (los lienzos abren en auto-fit, casi todo entra en viewport).

## 10. PARA EL MÓDULO DE MOTION GRAPHICS EN PARTICULAR

Esta es la única sección específica. Es la recomendación de **forma** del código — el producto
(qué hace el módulo, para quién, qué formatos) lo define Fran en el Norte del módulo, y va en
`docs/modulos/motion/README.md`.

### 10.1 El motor es una librería pura; la UI es una cáscara

Separá desde el primer día:

```
lib/motion/
  modelo.ts          ← tipos: Composicion { ancho, alto, fps, duracion, capas: Capa[] } · Capa · Propiedad · Keyframe · Easing
  keyframes-puro.ts  ← interpolar(keyframes, t), easings con nombre, holds, bezier
  evaluar-puro.ts    ← estadoEn(composicion, t): el árbol de capas RESUELTO para un instante (posición, escala, rotación, opacidad, texto…)
  pintar.ts          ← pintar(estado, ctx: CanvasRenderingContext2D | OffscreenCanvasRenderingContext2D) — DETERMINISTA
  serializar-puro.ts ← JSON ↔ modelo, con versión de esquema (`{ version: 1, … }`) y migrar() entre versiones
  validar-puro.ts    ← invariantes (un keyframe fuera de la duración, un fps que no es entero…)
  camara-puro.ts     ← la matemática de cámara con las funciones de §8.3 (la reemplazamos por lib/canvas al integrar)
components/motion/
  Editor.tsx         ← el shell: lienzo + timeline + inspector (client)
  Lienzo.tsx · LineaDeTiempo.tsx · Inspector.tsx · Capas.tsx
```

Por qué: **`estadoEn(comp, t)` + `pintar(estado, ctx)` es lo único que tiene que ser perfecto**.
Si es puro y determinista, (a) se testea con `node:test` sin browser (con un canvas falso que
registra las llamadas), (b) el preview y el export usan **la misma función** (lo que ves es lo
que sale), (c) Diosa puede generar o editar composiciones sin tocar la UI (§10.5), y (d) el día
que cambiemos el lienzo, el motor queda.

### 10.2 El modelo de datos

- **Una tabla `motion_composicion`** con el patrón de §2.4: `id`, `proyectoId`, `ownerId`,
  `nombre`, **`contenido` (jsonb: la composición serializada, con `rev` adentro y `v` por
  capa/keyframe)**, `thumbnailUrl`, `renderId` (nullable: el id en el catálogo de media del último
  render), `createdAt`, `updatedAt`. Aditiva, sin FKs hacia tablas que no existen.
- **Las capas referencian media por id del catálogo** (`playground_media.id`), nunca por URL
  cruda: las URLs son firmadas y expiran; el id es estable y el server resuelve la URL al cargar.
  El poster/thumb de un video se deriva del nombre del asset por convención (`.poster.webp`,
  `.thumb.webp`), sin columna.
- **Fuentes:** el repo **no tiene webfonts** (la UI usa el stack del sistema) ni precedente de
  carga de fuentes para render; para texto animado vas a tener que resolver la carga (`FontFace`
  + `document.fonts.load`) y **decirlo en `ENTREGA.md` con las licencias**. Los logos de marca
  existen como SVG (`public/brand/`) y como paths (`marcas.ts`): se pueden ofrecer como «capa de
  forma» lista.
- **Versión de esquema en el JSON y `migrar(datos)` desde el día uno**: la composición guardada
  hoy tiene que abrirse en seis meses.

### 10.3 Preview y render son dos caminos con la misma función

- **Preview** en el browser: canvas 2D (WebGL sólo si lo justificás — hoy el repo no tiene ni
  WebGL, ni WebCodecs, ni `OffscreenCanvas`), `requestAnimationFrame`, reloj propio (no
  `setInterval`), `pintar(estadoEn(comp, t))`. Con la pestaña oculta, pausa. Con reduced-motion,
  reproduce igual (es contenido). Y el `<canvas>` respeta el tema al pintar el chrome (§3.5).
- **Render a video: decidilo con nosotros antes de construirlo.** Las dos opciones honestas:
  (a) **en el browser** con WebCodecs (`VideoEncoder`) pintando frame a frame en un
  `OffscreenCanvas` y muxeando con **`mp4-muxer`, que ya está en las dependencias** (junto con
  `mp4box`), subiendo el resultado al catálogo de media — sin costo de server, depende del
  browser; (b) **en el server** con `ffmpeg` — el repo lo usa por `spawn` en UN script de
  reuniones, **no en serverless** (las funciones tienen 300 s y no traen ffmpeg): necesitaría un worker
  aparte. La (a) es la que entra sin infraestructura nueva. El precedente que existe hoy es
  `RecorteVideo`/`ConvertirVideo`: `<canvas>` + `MediaRecorder`/`captureStream` para cortar y
  reencodear en el cliente, más `faststart.ts` (remux puro del `moov` al frente antes de subir)
  y `lib/video/comprimir.ts` (política de compresión). **`MediaRecorder` no es frame-exacto**: para
  un render determinista el camino es WebCodecs. En cualquier caso, el frame lo pinta **la misma
  `pintar()`**.
- **Audio**: si hay pista, el preview la reproduce con `<audio>` sincronizado al reloj (y
  `usePausarLoDeAtras` cuando se abre algo encima); el render la muxea. Si no la hay en esta
  versión, decilo.

### 10.4 Dependencias que SÍ pueden justificarse acá

Un motor de easing/bezier chico, `opentype.js` si hay texto animado con outlines, un muxer para
WebCodecs (`mp4-muxer` **ya está**; `webm-muxer` si hace falta VP9). **Cada una con su peso y
cargada sólo en la page del módulo** (§9). Lo que no: un motor de animación de UI, un editor de
timeline «listo», React Flow / Konva / Fabric / tldraw (los lienzos del repo son propios, y el
tercero también), `lottie-web` como runtime de la UI (importar/exportar Lottie como FORMATO es
otra cosa, y sería un buen `P1`).

### 10.5 Pensá en Diosa desde el principio

El asistente de diosa opera los módulos a través de **tools** (funciones con nombre, args tipados
y descripción) declaradas en un catálogo tipado (`HerramientaDiosa = { nombre, skill, descripcion,
entidades… }` — el `skill` y las tablas que lee están tipados: no compila si el área o la tabla no
existen) y agrupadas por **área**, que se activa por la ruta (`AREA_POR_RUTA`). No las escribas vos
(necesitan el motor del asistente), pero **dejá el motor listo para ellas**:
`crearComposicion(desde: Brief)`, `agregarCapa(comp, capa)`, `moverKeyframe(comp, capaId, prop,
t, nuevoT)`, `describir(comp): string` — funciones puras que reciben y devuelven la composición.
Si eso existe, cada tool son diez líneas y el área `motion` se registra en una tarde.

### 10.6 Lo que va a distinguir una buena entrega

- El motor tiene **más tests que la UI** y un sabotaje visto en rojo por invariante.
- Un JSON de composición de ejemplo en `tests/motion/fixtures/` que ejercita **todo** el modelo.
- El preview a 60 fps con 20 capas y texto **medido** (un número en `ENTREGA.md`, no una
  impresión), en claro y oscuro.
- El editor se siente como los otros dos lienzos (§8.3) sin que nadie se lo tenga que explicar:
  mismas teclas, mismo zoom al cursor, mismo snapping azul, mismo «⌘Z deshace un gesto entero».
- El primer render sale por el catálogo de media y aparece en la galería del proyecto como
  cualquier otro asset.

## 11. LO QUE NO SE HACE (lista negra)

| ❌ | Por qué |
|---|---|
| Controles nativos (`<select>`, `type="date"`, `type="range"`, `type="checkbox"`) fuera de `ui/` | se ven de otra aplicación y abren chrome del browser en inglés |
| SVG inline / librerías de íconos | nueve versiones del mismo trash |
| Colores fuera de paleta, hex o `rgb()` sueltos en el JSX | rompen el modo oscuro y la identidad; hay un guardián |
| Azul `#0005FF` como texto sobre fondo oscuro | 1.8:1, ilegible |
| Verde para «ok» | la paleta no tiene verde; `--ok` es azul |
| `title=` nativo | es `<ConPista>` |
| `localStorage` / `sessionStorage` para estado de la app | la única excepción es preferencias de UI, y ya tiene su patrón (clase en `<html>`) |
| `transition: all`, animaciones ad-hoc, `transform` en una capa con blur, `translateY` al hover | rompen el vidrio y el lenguaje único |
| Librerías de UI, de animación de UI, de estado global, de canvas | no hay y no se agregan |
| `moment`, `dayjs`, tablas de meses propias, `toLocaleDateString("es-AR")` a mano | hay un helper único de fechas; había 22 tablas de meses y la app decía la misma fecha de dos formas |
| Texto de UI en inglés, `t(variable)`, `` t(`…${x}`) `` | el castellano es la clave y el guardián lee literales |
| Un `"use client"` que importa valores de la capa de datos | la base entra al bundle y la página revienta en runtime con el build verde |
| Confiar en un id que llegó del cliente · un parámetro de permiso opcional | IDOR · un candado que no llega aprueba en silencio |
| Escribir afuera (storage, API) antes de validar todo | deja huérfanos irrecuperables |
| Un `switch` dato→UI sin `default` que degrade | otra sesión mete un valor nuevo y tumba la sección |
| `will-change` por elemento · `backdrop-filter` dentro de un lienzo | cientos de capas de compositor por frame |
| `z-index` ≥ 9000 | la banda es del sistema |
| Prometer «pantalla negra tipo Netflix» o «detectar capturas» | no existe en una web: sólo la marca de agua hace la fuga atribuible |
| Scripts en tu entrega que toquen una base, `pkill`, `rm -rf` | no hay base de juguete donde probarlos; nada que toque datos se corre sin leerlo |
| Un comentario que describe un comportamiento que el código no tiene | la prosa envejece hacia el optimismo; escribí el porqué, no el qué |

### F. La firma real del traductor (`src/lib/i18n/traducir.ts`)

Tu stub tiene que cumplir esta interfaz, así el reemplazo es un import:

```ts
export interface Traductor {
  (clave: string, vars?: Vars): string;
  readonly idioma: Idioma;
  plural(n: number, singular: string, plural: string, vars?: Vars): string;
  ctx(contexto: string, clave: string, vars?: Vars): string;
  rico(clave: string, huecos: Huecos): ReactNode;
}
```

`t(x)` en castellano es la identidad (no hay diccionario `es`); el inglés vive en `src/lib/i18n/diccionarios/<zona>.ts` como `Record<castellano, inglés>` y cada zona se suma al spread de `index.ts`. Tu módulo trae su zona (`motion.ts`) con las claves que usó.
